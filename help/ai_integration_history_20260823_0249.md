# 매칭 프로젝트 AI 연동 및 테스트 기록

이 문서는 매칭 프로젝트를 진행하면서 회원의 성향(Traits) 데이터를 분석하기 위해 AI API를 도입하고 테스트했던 과정과 겪었던 문제들, 그리고 최종적으로 적용된 아키텍처를 기록하기 위해 작성되었습니다.

## 1. 초기 목표 및 AI 도입 배경
단순히 랜덤 숫자로 생성된 더미 데이터를 사용하면 매칭 알고리즘이 제대로 작동하는지 검증하기 어렵다는 문제가 있었습니다. 따라서 사용자의 직업, 취미, 이상형, 자기소개 등의 텍스트를 분석하여 14가지 세부 매칭 지수(0~100점)를 정교하게 추출해 내는 AI(Gemini)를 도입하기로 결정했습니다.

## 2. 모델 선택과 버전 마이그레이션 이슈

### 구버전 모델의 한계
초기에는 gemini-1.5-flash 모델을 염두에 두었으나, 이미 2026년 기준으로 구버전이 되어 사용이 원활하지 않았습니다.

### gemini-3.5-flash 도입과 일일 호출 제한
차선책으로 gemini-3.5-flash를 적용하여 테스트를 진행했습니다. 하지만 이 모델은 무료 티어에서 하루 호출 제한(20 Requests Per Day)이라는 극단적인 제약이 걸려 있었습니다. 테스트 코드로 30건을 돌리자마자 바로 429(Rate Limit Exceeded) 에러가 발생하며 테스트가 중단되었습니다.

### gemini-3.6-flash 도입 및 1분당 호출 제한
최종적으로 일일 제한이 넉넉하고 최신 모델인 gemini-3.6-flash로 마이그레이션했습니다. 이 모델은 일일 제한은 넓지만 1분당 15회(15 RPM)의 호출 제한이 있었습니다. 이를 극복하기 위해 배치 스크립트 단에서 딜레이를 주는 방어 로직이 필요해졌습니다.

## 3. 구조적 개선: DB를 통한 동적 AI 설정
AI 모델의 버전이 빠르게 바뀌고, 향후 API 키나 URL이 변경될 때마다 백엔드(Spring Boot) 서버를 껐다 켜거나 재배포해야 하는 문제가 있었습니다.
이를 해결하기 위해 ai_config라는 데이터베이스 테이블을 설계했습니다.

- api_key뿐만 아니라 api_url까지 DB에서 관리하도록 개선
- Spring Boot가 구동될 때뿐만 아니라, 운영 중에도 DB 값만 바꾸면 즉시 새로운 AI 모델이나 새로운 API 주소를 바라보도록 유연성 확보

## 4. 회원 대량 생성기(배치 스크립트) 설계 및 트러블슈팅

### 목적
실제 사람과 유사한 고품질 회원 데이터 3,000명을 백그라운드에서 자동 생성(batch_generate_members.js)하여 매칭 알고리즘을 테스트하기 위함이었습니다.

### 발생했던 문제 1: 429 RPM 제한
Gemini 3.6 Flash의 1분당 15회 제한을 회피하기 위해, 1명의 회원을 생성할 때마다 7초간 강제로 휴식(Sleep)하는 방어 로직을 추가했습니다. 그럼에도 간헐적으로 제한에 걸릴 경우를 대비해, 429 에러 응답 시 30초를 대기했다가 다시 시도하는 재귀적 복구 로직을 구현했습니다.

### 발생했던 문제 2: AI Safety 필터 차단
랜덤으로 조합된 자기소개 텍스트 중 구글 AI의 내부 안전 필터(Safety Filter)에 걸리는 단어가 섞여 있을 경우, AI가 응답을 거부하는(500 에러) 현상이 발생했습니다. 이 경우 해당 회원은 실패 처리하고 다음 회원 생성으로 넘어가도록 예외 처리를 강화했습니다.

### 발생했던 문제 3: 트랜잭션 중복(Duplicate Entry) 에러
배치 시작 시 테이블을 Truncate한 직후, 백엔드와 DB의 순번 초기화 타이밍 문제로 인해 최초 1건에 대해 member_trait 테이블에서 Unique Constraint 예외가 발생하는 이슈가 있었습니다. 스크립트가 에러를 무시하고 롤백 후 다음 회원부터 정상 진행하도록 조치했습니다.

## 5. 기타 트러블슈팅 및 교훈

- PowerShell 인코딩 문제: 윈도우 환경에서 PowerShell 스크립트(Set-Content)로 한글이 포함된 파일을 조작할 때, BOM이 주입되거나 UTF-8 인코딩이 깨지면서 빌드가 완전히 망가지는 치명적인 문제가 있었습니다. 이후 파일 수정은 반드시 정식 도구를 사용하도록 원칙을 세웠습니다.
- 고스트 프로세스: 백엔드를 껐다 켤 때 java.exe가 비정상적으로 남아 8080 포트를 점유하는 현상이 잦았습니다. 시작 스크립트를 짤 때 taskkill /F /IM java.exe를 먼저 실행하여 환경을 깔끔하게 정리하는 과정을 추가했습니다.

## 6. 결론 및 유료 티어(Pay-As-You-Go) 전환
초기에는 1명당 약 15~20초씩 소요되며 하루 20번 한도에 부딪혔으나, 실무 수준의 대용량 테스트를 위해 과감하게 유료 결제(Pay-As-You-Go) 모드로 전환하였습니다. 
- API 요금 폭탄을 막기 위해 구글 클라우드 콘솔에 월 예산($3) 알림 및 하루 5,000번의 하드 리미트(Quota) 할당량 제한을 설정해 완벽한 안전장치를 마련했습니다.
- 유료 티어 전환 후 RPM 제한이 1,000으로 대폭 상승함에 따라, 기존에 스크립트에 걸어두었던 '7초 대기' 방어 로직을 걷어냈습니다.
- 결과적으로 저렴한 비용(몇 백 원 수준)으로 속도 제한 없이 초고속으로 3,000명의 정교한 리얼 데이터를 쏟아붓는 강력한 파이프라인이 완성되었습니다. 이를 바탕으로 매칭 알고리즘의 정확도를 신뢰성 있게 검증할 수 있게 되었습니다.
